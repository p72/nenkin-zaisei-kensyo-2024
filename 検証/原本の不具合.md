# 原本のコードで見つかった不具合・癖の台帳

厚生労働省が公開した計算プログラム（資料001365945、.c/.cpp が 111本・
35,842行、.h が 34本・2,366行）を
動かし、Python へ移植する過程で見つかったものを記録する。

**原本には一切手を入れていない。** 動かすために必要な変更は
`検証/実行/patches/glibc-portability.patch`（実質29行）と
`検証/実行/run_pipeline.sh` の書き換え処理に限られ、いずれも計算結果に
影響しないことを差分テストと公表値照合で確認している。

## 読み方

| 区分 | 意味 |
|---|---|
| **A** | 落ちる。動かすのにパッチが必要だった |
| **B** | 未定義動作だが、出力には出ない（証明を添えた） |
| **C** | 前提を変えると落ちる（絶対パスの長さなど） |
| **D** | 値が入らない。出力の列が常に 0 になる |
| **E** | 不具合に見えるが結果を支えている。直してはいけない |
| **F** | デッドコード |
| **G** | ビルドの指定で結果が変わる |
| **H** | 未初期化・解放済みの値が出力に出る（値そのものは移植版では再現できない） |
| **I** | 集計の取りこぼし。「計」の添字が 0 のまま残る |
| **J** | 数値の写し間違い（桁のずれ）。**結果が変わる** |
| **K** | 出力が上書きされる。制度をまたいで同じファイル名 |

「出力に出る／出ない」は、原本の C と移植版 Python を同じ入力で走らせて
**バイト単位で比べて**確かめている（⑤は出力14ファイル690MBで不一致0）。

## A. 落ちる — `fclose` の誤りが5箇所

原本を glibc で動かすと、ファイルを閉じるところで5箇所落ちる。**中身は
2種類**で、直し方も違う。

| # | 場所 | 何が起きるか | いつ落ちるか |
|---|---|---|---|
| A1 | `厚生年金/収支計算/fcls.c:64` | `fclose(NULL)` | **通常試算で必ず** |
| A2 | `厚生年金/給付費推計/fileio.cpp:328` 付近 | `fclose(NULL)` | ② の実行中 |
| A3 | `基礎年金/main.c:104` | **同じストリームの二重クローズ** | ④ の実行中 |
| A4 | `基礎年金/printout.c:151` | **同じストリームの二重クローズ** | ④ の実行中 |
| A5 | `基礎年金/read_cut.c:61-62` | `fclose(NULL)` | **調整期間の一致のときだけ** |

### A1・A2・A5 — `fclose(NULL)`

glibc の `fclose(NULL)` はヌルポインタを参照して SIGSEGV になる。原本は
「開いていないかもしれないファイル」を無条件に閉じている。

```c
/* fcls.c:64 — Touitu==0（通常試算）では開いていない */
fclose(ifp_Touitu);

/* read_cut.c:61-62 — infile.csv のフラグ B・C で片方しか開かない */
fclose( fp_in[CUT] );
fclose( fp_in[CUT_K] );
```

A5 は **④を2回まわす経路（調整期間の一致オプション）でしか通らない**ため、
通常試算では起きず、オプション試算を実装するまで見つからなかった
（終了コード 139 で発覚）。

`if(fp != NULL)` の守りを足すだけで直る。

### A3・A4 — 同じストリームを2回閉じる

こちらは `NULL` ではなく、**既に閉じた `FILE *` をもう一度閉じる**。
glibc は `fclose` で `FILE` の領域を解放するので、2回目は解放済み領域への
書き込みになり、ヒープが壊れて異常終了する（`free(): double free` など）。

```c
/* main.c:104 — read_file.c:79 が既に fclose( fp_in[DOKUZI] ) している。
   DOKUZI は 0 なので同じストリーム */
fclose( fp_in[0] );

/* printout.c:151 — printout() は main.c から2回（引数 0 と 1）呼ばれる。
   1回目で閉じたあと、2回目は閉じたストリームへ書いてから また閉じる */
fclose( fp_out[OUTPUT] );
```

A4 は「閉じたあとに書く」も伴うので、`fclose` を消すだけでは足りない
（消したうえでプロセス終了時のフラッシュに任せる）。④の `output.csv` は
追記モード（`a`）で、`printout(0)` が枯渇年度、`tyousei()` が代替率と
終了年度、`printout(1)` がまた枯渇年度を書くので、**3回に分けて同じ
ストリームに書く**設計になっている。

いずれも閉じるだけの話なので計算結果は変わらない。移植版は「閉じない」で
そろえてあり、④の出力7ファイルが原本とバイト一致することで確かめている。

## B. 未定義動作だが出力には出ない

### B1. `class02` のコピーコンストラクタが2つのフィールドを写さない

`分布推計/prog02.cpp` は `set_var001` から `set_var032` まで並べたあと、
**`set_var035`** に飛んでいる。`var033` と `var034` が抜けている。

```c
  set_var031(arg02a.var031);
  set_var032(arg02a.var032);
  set_var035(arg02a.var035);   /* ← var033, var034 が無い */
  set_var036(arg02a.var036);
```

メンバ初期化子も無いので、C++ ではコピー後の `var033`/`var034` は**不定値**。

さらに悪いことに、`class02` はコピーコンストラクタを宣言しているため
**ムーブコンストラクタが暗黙に作られない**。`std::stable_sort` の要素の
入れ替えも `std::vector` の再確保も**コピーを通る**ので、
**ソートするたびに壊れる**。

**それでも出力には出ない。** `main.cpp` の年次ループがこの順になっている。

```
198行  stable_sort(… compare_var037())   ← ここで壊れる
200行  func09c(…)                        ← 全員に set_var033/034
218行  func10d(…)                        ← ここで初めて読む
```

`var033`/`var034` を読むのは `func10d`（`prog10.cpp:547-553`）だけで、
`func09c`（`prog09.cpp:181-182`）は if/else の**外**で全員に無条件に代入する。
つまり「壊れる → 必ず書く → 読む」の順序になっている。

### B2. `rd_drec` が範囲検査の前に代入する

`厚生年金/収支計算/stdfun.c:26-34`。

```c
ctemp[j] = '\0';
ddata[num_comma] = atof(ctemp);      /* ← 先に書く */
if(num_comma<num_data){              /* ← 検査は後 */
    num_comma++; j = 0; i++;
}else{
    printf("rd_drec()が読み込み可能データ数を超えています。[%s]\n", rec);
    exit(1);
}
```

`num_comma == num_data` に達した行では `ddata[num_data]` に**配列の外へ1つ
書いてから** `exit(1)` する。呼び出し側は `double dtemp[7]` や `double
dtemp[100]` のようなスタック上の配列なので、スタックを1要素踏む。

直後に終了するので観測できる影響は無いが、`_FORTIFY_SOURCE` や
AddressSanitizer を有効にすると検出される。

### B3. `var09c6` が初期化されないまま読まれうる

`分布推計/prog09.cpp:89`。宣言だけして if/else if の連鎖で決めているが、
**`else` が無い**。

```cpp
int var09c6;                                   /* 初期化なし */
if ( arg09c2[p].get_var006() % 10000 == 101 ) {
  var09c6 = 8;
} else if ( arg09c2[p].get_var006() % 10000 <= 201 ) {
  var09c6 = 9;
...
} else if ( arg09c2[p].get_var006() % 10000 <= 1231 ) {
  var09c6 = 8;
}                                              /* ← else が無い */
```

`var006 % 10000` が **1231 より大きい**と、どの枝にも入らないまま
`var09c2 = var09c6;` などに使われる（未定義動作）。月日として正しい値
（0101〜1231）なら必ずどれかに当たるので、実データでは起きない。

なお `var006` の初期値は **-1**（`_prototype.h:65`）で、C の `%` は
0方向に丸めた商の余りなので `-1 % 10000 == -1` → `<= 201` に当たって
`var09c6 = 9` になる。Python の `%` は `9999` を返すので**そこは違う**。
移植では C の剰余を明示的に書いた（`bunpu/prog09.py` の `_cmod`）。

### B4. `read_csv` の `previous_c` が初期化されないまま読まれうる

`被保険者推計/stdfm.c:57,90`。

```c
int c ;
int previous_c ;                                     /* 初期化なし */
...
while ( ( ( c = fgetc(fp) ) != EOF ) && ( c != '\n' ) ) {
  ...
  previous_c = c ;                                   /* 本体の中で代入 */
}
if ( previous_c != ',' ) {                            /* ← 本体が回らないと未初期化 */
```

**行の1文字目が `'\n'`（＝空行）だと `while` の本体が1回も回らない**ので、
`previous_c` は未初期化のまま比較される。空行を読むと起きる。

gcc/x86-64 では直前のスタックの値が入り、ほぼ常に `','`（44）ではない
ので、「行末のフィールドをもう1つ読む」側に入る。結果として空行では
`buffer[0]` に `atof("")` ＝ 0.0 が入り `data_number` は 0 になる。
移植版はその挙動に合わせた（`検証/移植/hihokensha/cnum.py`）。

同梱の入力に空行があるかは確かめていない。`read_csv` は `while` で
EOF まで読む使い方が多いので、行末の改行の直後で1回起きうる。

### B7b. ②の `csvio::split` はカンマの無い行で同じ値を2つ返す

`厚生年金/給付費推計/sepslib.cpp:70-93`。

```cpp
string::size_type last = str.find_first_of(',');      /* npos になりうる */
while(first < str.size()) {
  ...
  result_vals.push_back( string(str, first, last - first) ) ;
  first = last + 1;                    /* npos + 1 == 0（符号なし） */
  last = str.find_first_of(',', first);
  if(last == string::npos) last = str.size();
}
```

カンマが1つも無い行だと1周目の `last` が `npos` のままなので、
`string(str, 0, npos)` は文字列の末尾までを取る。そのあと
`first = npos + 1` が**符号なしのまわりこみで 0 に戻る**ので、
2周目でまったく同じ文字列をもう1つ積む。3周目は `first = size + 1` で
止まる。つまり**同じ要素が2つ**並ぶ。

`last` を `npos` のままにしないのは2周目以降だけ（`if(last == npos)
last = str.size();` が `first` の更新より**後**にある）ので、
1周目だけこの抜けが残る。

②の入力はどれもカンマ区切りなので実害は無いが、空行（`"\n"` だけの行）
を読むと「0 が2つ」になる。移植版も同じふるまいにしてある
（`csvio.py` の `split`）。

### B7c. ②の `fopn` は `stringstream` を紙一重で使い回している

`厚生年金/給付費推計/fileio.cpp:21-30`。

```cpp
stringstream ss;
ss << setw(4) << setfill('0') << iname << "\n";  ss >> cname;
ss << setw(4) << setfill('0') << iwname << "\n"; ss >> cwname;
ss << setw(4) << setfill('0') << iecon << "\n";  ss >> cecon;
```

1つの `stringstream` に3回書いて3回読む。`>>` は文字列を読んだあと
**区切りの `'\n'` を読み残す**ので eofbit が立たず、次の `<<` が効く。

もし `"\n"` を付けずに書いていたら、1回目の `>>` で eofbit が立ち、
2回目以降の `<<` と `>>` が**何もしなくなる**（`cwname` と `cecon` が
空文字列のまま）。パスが `.../rslt/waku-05.csv` のように壊れて
`fopen` に失敗し、そこで初めて気づくことになる。

移植版は `"%04d"` で同じ文字列を作る。

### B8. 呼び出し側の `buffer` が初期化されず、列の足りない行で前の値を拾う

`基礎年金/stdfm.c:96` の `read_data` は **`buffer[0..*data_number_ptr]`
にしか書かない**。呼び出し側の

```c
double buffer[DATA_MAX] ;                /* 初期化なし。DATA_MAX は 1000 */
```

は初期化のない自動変数で、同じ関数の中の `read_data` 呼び出しで
使い回される。つまり

- **1回目**は不定値（スタックに残っていた値）
- **2回目以降**は前の行の値

が読み切った個数より先に残る。`ReadHiyousha` は旧法老齢の行で
`buffer[6..13]` の8列を読むが、他の行は6〜11列しかないので、
**列の少ない行を読んだ直後に列の多い行の見出し検査が通れば前の行の値が
混ざる**（同梱データは列数が揃っているので起きない）。

移植版は `cnum.Buffer`（関数ごとに持ち回る list）で同じふるまいにし、
最初だけ 0.0 にしてある。原本の1回目の不定値は再現できないので、
**出力がバイト一致することで「そこには届かない」ことを確かめている**。

### C6. ④の `Round` は割る向きが逆で、しかも `int` を返す

丸め関数は**システムごとに3種類**あり、名前が似ているのに中身が違う。

| システム | 関数 | 中身 | 戻り値 | `x, 1` の意味 |
|---|---|---|---|---|
| ⑤ 収支計算 | `nround(x, n)` | `round( x * 10^n ) / 10^n` | `double` | 小数第1位へ |
| ① 被保険者推計 | `raund(a, b)` | `(int)( a * 10^b ± 0.5 ) / 10^b` | `double` | 小数第1位へ |
| ④ 基礎年金 | `Round(a, b)` | `(int)( a / 10^b + 0.5 ) * 10^b` | **`int`** | **10 の位へ** |

```c
/* 基礎年金/stdfm.c:174 */
int Round( double a , int b )
{
	int c , d , i , S ;
	S = 1 ;
	for( i = 1 ; i <= b ; i++ ) S *= 10 ;
	a /= S ;                 /* ← ① は a *= S */
	d = (int)( a + 0.5 ) ;   /* ← ① は a>0 で ±0.5 を分ける */
	c = d * S ;
	return( c ) ;            /* ← int。小数点以下が消える */
}
```

違いは3つ。

1. **割ってから掛け戻す。**`Round(1234.5678, 1)` は 1230、
   ①の `raund(1234.5678, 1)` は 1234.6。取り違えると桁が 100 倍ずれる。
2. **`int` を返す。**小数点以下が必ず消える。
3. **負の値で 0 方向に寄る。**`±0.5` の場合分けが無いので
   `Round(-1234.5678, 1)` は -1220（①なら -1230 相当）。

呼び出しは `read_file.c:403` の `Round( Hokenryou_m , 1 )` だけで、
保険料月額を 10 円単位に丸める用途なので 1.〜3. のどれも都合が合っている
（保険料は正で整数）。名前が紛らわしいだけ。

移植版は3つを別の関数として持ち、`int` に収まらない組では例外にする。

## G. ビルドの指定 — `-Ofast` で結果が変わる

### G1. ⑥分布推計の Makefile が `-Ofast` を指定している

`-Ofast` は `-ffast-math` を含み、そこに `-fno-signed-zeros` が
入っているため **−0.0 が +0.0 になりうる**。同じ行の4列目は
`-Ofast` でも `-0.00000` のままなので、全部が消えるわけではない。

**大きさは 1e-9 以下。** 違いはどれも倍精度の最後の桁あたりで、
値の大きさ（1e4〜1e14）に対して 1e-11 〜 1e-16 の相対差。
公表値は有効数字がずっと粗いので、この大きさで丸めた表示が
動くことはない。ただし**公表値との照合（3,977項目・不一致0）は
`-Ofast` ビルドの出力で通したもの**で、`-O2` で建て直したあとの
再照合はまだしていない。

**⑥とは桁違いに効く。** G1 の⑥は 36ファイルのうち**1ファイルの
1桁**だけだったのに、②は12本のうち11本・のべ 100万 欄以上が動く。
⑥は最後に割り算を1回するだけなのに対し、②は 105 年度 × 年齢 ×
経過年の漸化式を延々と回すので、**1回の書き換えが次の年度に
持ち越されて広がる**（`f[x] = f[x-1] * 残存率 * 改定率 + fn[x]`）。
差が 1e-11 どまりで済んでいるのは、漸化式が発散する形では
ないため。

**直した。** `run_pipeline.sh:300` を `-O2` に変えた（⑥は Makefile
自身が `-Ofast` を指定しているので G1 のとおりそのまま）。
移植版の突き合わせは初めから `-O2` で建てたハーネスとしているので、
**移植版と原本の `-O2` ビルドが一致する**という結論は変わらない。

### H3. `pstat` の `csv::join(...).c_str()` が解放済みの領域を指す

`厚生年金/給付費推計/pstat.cpp:11-35, 117, 149`。

```c

  const char * join2(const v2_t &v, int axis1, int exp) {
    v1_t vals;
    for(int jj = 1; jj <= 2; jj++) vals.push_back(v.AT(axis1, jj) * pow(10.0, exp));
    return csvio::join("%16.8lf", vals).c_str();      /* ← ここ */
  }
  const char * sum1_join2(const v2_t &v, …) { … return csvio::join("%16.8lf", vals).c_str(); }
  const char * join1   (const v2_t &v, …) { … return csvio::join("%16.10lf", vals).c_str(); }
}
```

`csvio::join` は `std::string` を**値で**返す。`.c_str()` はその
**一時オブジェクトの中の**バッファを指す。`return` 文が終わった時点で
一時オブジェクトは壊されるので、返った `const char *` は
**解放済みの領域を指す**。呼ぶ側は

```c
fprintf(fp, "%s,%s,%s\n", "総給付費", hikaku_ns::join2(tmq, 1, -12), "兆円");
```

と、そのまま `%s` に渡す。`pstat.cpp:117` と `:149` にも

```c
const char *ctmw = csv::join("%16.8lf", …).c_str();
```

の形が2つある（こちらは一時オブジェクトが文の終わりまで生きるので、
次の文で使う時点でもう壊れている）。

**出力に出る。実測した。** 段階テスト（`検証/移植/test_kyufu_stage.py`
の `out` 段階、g++ 13 / `-O2`）で原本と移植版の出力を突き合わせると、
`pstat()` が書く3本だけが食い違う。

| ファイル | 行数 | 化けた行 | 化けたバイト列 |
|---|---|---|---|
| `hikaku.3001-3001-3001` | 216 | 130 | 120行が `cd ed d9 63 a1 55`、10行が `57 e3 4e 5a 05` |
| `ashimotosum.3001-3001-3001` | 581 | 360 | 360行が `57 e3 4e 5a 05` |
| `ashimotossum.3001-3001-3001` | 581 | 360 | 360行が `57 e3 4e 5a 05` |

行数・見出し・単位の欄は合っていて、**`hikaku_ns` の3つが作る数値の欄
だけ**が数バイトのごみに化ける。たとえば

```
                            ┌ 本来の値（移植版）
総給付費,     26.40777389,     24.36361335,兆円
総給付費,<cd ed d9 63 a1 55>,兆円          ← 原本
```

ごみが2種類なのは、確保する大きさが2通りあるため。
`join2` / `sum1_join2` は 2 個 × `%16.8lf` ＋ カンマ = **33 文字**、
`join1` は 13 個 × `%16.10lf` ＋ カンマ = **220 文字**で、別の
大きさの区画から取る。解放済みの区画に `malloc` の空きリストの
つなぎが書き込まれているので、**同じ区画を使い回す呼び出しはすべて
同じごみ**になる（120回・360回とも1種類）。

**同じバイナリ・同じ入力でも毎回変わる。** 2回続けて走らせて
比べた。

| | `join2` 系（120行） | `join1` 系（10行） |
|---|---|---|
| 1回目 | `e1 63 18 5e 33 56` | `6b 21 6f 63` |
| 2回目 | `51 0e 63 6e 59 55` | `bb 03 cf 55` |

**化ける位置は同じ130行**で、バイト列だけが変わる。長さまで
変わるのは、ごみを NUL までの文字列として読むので、
たまたま 0x00 が現れる位置が動くため。

原因は **ASLR**。末尾が `0x55` `0x56` なのは PIE の
ヒープ／mmap の番地の上位バイトで、解放済みの区画に残った
**ポインタの値を文字として読んでいる**ことの裏付けになる。
番地は起動ごとに変わるので、ごみも変わる。

```
$ setarch -R ./h out    # ASLR を切って2回
→ 2回とも同じ出力になる
```

つまり `hikaku` と `*sum` は、**同じプログラム・同じ入力でも
実行のたびに違うファイルになる**。再現しない出力である。

ビルドの指定でも変わる。`-O0` で建てても**化ける位置と行数は
同じ**（216行のうち130行）で、バイト列だけが変わる。

まとめると、**どの欄が失われるかは決まっているが、代わりに出る値は
決まっていない**。上に書いたバイト列はどれも再現の保証が無い。

`hikaku` `ashimoto*` は**確認用のファイル**で、②のほかの
プログラムも③〜⑥も読まない。**財政検証の結果そのものは
これに影響されない。**

なお `pstat` の出力のうち `ashimoto` `ashimotos` は
`hikaku_ns` を通らないので**バイト一致する**（確かめた）。
化けるのは `hikaku` と `*sum` の2種類だけ。

**丸ごと1制度を通しても同じ結論。** 厚生年金を
KIJUN〜KE（105年度）で丸ごと走らせて、原本（`-O2`）と移植版の

| | 本数 | 大きさ |
|---|---:|---:|

| 食い違い（この項） | 3 | — |

## 移植版でどう扱ったか

| 区分 | 扱い |
|---|---|
| A | パッチ後の挙動に合わせる（`fclose(NULL)` は `if(fp != NULL)`、二重クローズは閉じない）。C 版もパッチを当てて走っているので |
| B | 観測できないので写さない。B1 は Python ではそもそもコピーが起きない |
| C | `run_pipeline.sh` と同じ規則でプレフィックスを付け替える |
| D | 常に 0 を出す（原本と同じ）。「代入が無い」とコメントに残す |
| E | **そのまま写す。** 理由と原本の行番号をコメントに書く |
| F | 未実装のまま残し、呼ばれたら `NotImplementedError` にする |
| G | `-O2`（IEEE どおり）に合わせる。突き合わせる C 版も `-O2` で建てる |

## この台帳の位置づけ

ここに挙げたのは**移植の過程で実際に踏んだもの**だけで、原本の全数調査では
ない。移植が済んだのは⑤収支計算・⑥分布推計・①被保険者推計・④基礎年金の
4システム（14,720行）と、②給付費推計のうち `cntl`〜`shke` の 5,680行ぶん。
**②の残り（約 4,600行）と③国民年金（11,067行）はまだ**なので、
同じ種類のものが残っている可能性が高い。

区分 **J**（数値の写し間違い）が2件とも②から出ていることを考えると、
残りにも同じ種類のものがある前提で進めるのが妥当だと考えている。
どちらも**検査が書かれていたのに効いていなかった**（J1 は検査自体が無く、
J2 は `assert` が `||` だった）という共通点がある。
