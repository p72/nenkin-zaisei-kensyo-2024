## なぜ「ビット一致」が狙えるのか

移植を始める前に、原本全体を機械的に走査した。結果が良かったので方針が決まった。

| 移植の障害になる構文 | 件数 |
|---|---:|
| `float`（単精度） | **0** |
| `long double` | **0** |
| `goto` | **0** |
| `union` | **0** |
| `memcpy` / `memset` / `memmove` | **0** |

浮動小数点が**全部 `double`**で単精度が1つも無い。Python の `float` は
IEEE 754 倍精度そのものなので、**演算の順序を保てば結果はビット単位で一致する**。

`pow` / `exp` / `log` / `sqrt` は49箇所だけ。CPython の `math` は libm を
そのまま呼ぶので、同一マシン上なら C と同じ値が返る。

型の分布は `double` 1,186 / `int` 1,942 / `long` 15 / `char` 140。

## 進め方

### 1. CSV 境界を利用する

6システムの唯一のインターフェースは CSV。だから**どのシステムも単独で
差し替えて検証できる**。C が作った入力を Python 版に食わせ、出力を C の
出力と比べればよい。⑤から着手しているのはこのため（所得代替率という
看板の数字が出るうえ、入力は既に手元にある）。

### 2. 原本を直接リンクしたハーネスで突き合わせる

`harness_*.c` が**原本の .c をそのままリンクして**呼び出し、計算後の
グローバル配列を `%a`（16進浮動小数）で吐く。`%a` は double を無損失で
文字列化するので、Python 側とビット単位で比較できる。

```
⑤ 収支計算
harness_cnum.c   → stdfun.c の nround()、C の round()・atof()
harness_econ.c   → econ.c（stdfun.c もリンク）
harness_cntl.c   → cntl.c と main.c の init_gval()/set_filenum()
harness_rdfl.c   → rdfl.c（init_gval→cntl→alfopen→flck→econ→rdfl まで通す）
harness_shus.c   → shus.c と shus_calc.c（上に続けて shus_calc8 まで通す）

⑥ 分布推計
harness_cppnum.cpp → C++ の書式（operator<< と setprecision）
harness_cppstd.cpp → std::mt19937(0) と libstdc++ の std::shuffle
harness_bunpu_io.cpp  → prog01〜04 の入出力
harness_bunpu_misc.cpp → prog07〜13 の細かい関数

① 被保険者推計
harness_hihoken_num.c → stdfm.c の raund() と read_csv()

④ 基礎年金

                        econ.c の round()

                        （原本の main.c と同じ「ガードを先に立ててから
                        include する」前置きを写したもの）
```

### 3. C の癖はコメントに残す

原本の不具合や不思議な挙動も、**直さずにそのまま写す**。理由を
コメントに書いて、原本の行番号を添える。直したくなったらまず
「公表値と一致するのはどちらか」を確かめる。

見つけたものは **[`検証/原本の不具合.md`](../原本の不具合.md)** に
台帳としてまとめている（落ちるもの・未定義動作・移植の前提を変えると
落ちるもの・値が入らない列・直してはいけない癖・デッドコード・
ビルドの指定で変わるもの・未初期化の値が出力に出るもの・
集計の取りこぼし・**数値の写し間違い**・**出力の上書き**の11区分、110項目）。

区分 **J** だけは他と性格が違う。**原本の答えが意図と違う**もので、
いま2件ある。

- **J1** 1936年度生まれの定額部分の読替率が1桁落ちている
  （`369` ／ 公表値は `1.369`）
- **J2** 地方公務員共済だけ、0〜1 の比に掛ける係数が
  `461.6518`（他の3制度は 0.79〜0.93）

どちらも移植版はビット一致を優先してそのまま写している。
2件とも「検査が書かれていたのに効いていなかった」（J1 は検査が無く、
J2 は `assert` が `&&` ではなく `||`）という共通点がある。

## 見つかった落とし穴

### `round()` は Python と C で違う

C99 の `round()` は「0 から遠い方へ」、Python の組込み `round()` は
「偶数へ」丸める。

```
C:      round(2.5) = 3.0    round(-2.5) = -3.0   round(0.5) = 1.0
Python: round(2.5) = 2      round(-2.5) = -2     round(0.5) = 0
```

⑤では `shus_calc.c:397,399` がモデル賃金（**所得代替率の分母**）で
`round()` を直接使っているので、ここを間違えると看板の数字が狂う。

さらに3つ、差分テストで実測して初めて分かった差があった。

1. **`math.floor(x + 0.5)` では代用できない**
   `x = 0.49999999999999994`（0.5 の直下の double）は `x + 0.5` が double では
   1.0 に丸まるため `floor` が 1 を返す。C の `round()` は 0。

2. **小数部は `trunc` を基準に取らないといけない**
   `floor` を基準にすると負の値で誤差が出る。
   ```
   x = -0.49999999999999994 = -(0.5 - 2^-54)
   floor(x) = -1.0
   x - floor(x) = 0.5 + 2^-54  →  double で表せないので 0.5 に丸まる
   ```
   「ちょうど半数」と誤判定して `-1.0` を返してしまう（C は `-0.0`）。
   `trunc` を基準にすれば差は必ず `(-1, 1)` に収まり、Sterbenz の補題で
   引き算が厳密になる。

3. **負のゼロ**
   C99 の `round()` は結果がゼロのとき引数の符号を残す。`round(-0.3) = -0.0`。
   `nround(x, -8)` のように桁を大きく落とすと実際に出てくる。

### `atof()` は 16進浮動小数も読む

`atof("0x10")` は C では 16.0。10進より先に16進を試さないと "0" になる。
また C の `atof()` は読めない文字列で**エラーを出さず 0.0 を返す**
（`stdfun.c:26` は末尾カンマの行で空文字列に `atof()` をかける）。

### `rd_drec()` は行末のフィールドを捨てる

フィールドは `,` か `\n` に出会った時にだけ確定する。行末に改行もカンマも
無いと**最後の値が落ちる**。

### Python の list では入らない

⑤のグローバル配列は合計 **628MB** ある。

```
D3bxtp[5][4][14][8][117][116]   30,401,280 要素   243MB
Kfpbxtp[5][4][14][8][117][116]  30,401,280 要素   243MB
Kofbxtp / Kofte / Kofkk          3,800,160 要素    30MB ×3
```

Python のネストした list だと 1 要素あたり参照8B＋floatオブジェクト32B で
**3.1GB** になって現実的でない。NumPy の float64 配列は C の double 配列と
**同じメモリ配置**（8B/要素、ゼロ初期化）なので 628MB のまま収まる。

ビット一致は崩れない。NumPy は「C と同じメモリ配置」としてだけ使い、
**演算はスカラーのまま**にしている。要素の読み書きは倍精度の厳密な転送で、
丸めが入る余地が無い。総和などのベクトル化は演算順序を変えてしまうので
入れない（速くするのは全部通してから）。

### 重要 — ベクトル化はビット一致を壊さない（縮約以外は）

上の最適化で結果が1ビットも変わらなかったのは偶然ではない。
**要素ごとの演算をまとめても、各要素にかかる演算の順序は変わらない。**

`shus_calc.c` 風のスカラー演算ループ（75万回の積和、k について逐次依存）を
書き方だけ変えて測ると、こうなる。**4つとも結果は同じビット列**。

| 実装 | 時間 | C 比 |
|---|---:|---:|
| **C（`-O2`）** | **0.005 秒** | 1× |
| Python NumPy ベクトル化（k は逐次、s/u/x を一括） | **0.025 秒** | **5×** |
| Python 素の list でスカラー | 0.171 秒 | 34× |
| Python NumPy のスカラー添字 | 0.831 秒 | 166× |

ここから移植の方針が2つ決まる。

1. **要素ごとの演算は最初からベクトル化してよい。** ビット一致は保てる。
2. **NumPy のスカラー添字は素の list より5倍遅い。** 大きな配列は
   メモリの都合で NumPy にせざるを得ないが、内側のループで要素ごとに
   触るのは最も遅い使い方。ベクトル化するか、必要な部分を list に
   取り出して回してから書き戻す。

順序を変えてはいけないのは**縮約**（総和・総乗）だけ。NumPy の `np.sum` は
対数的に足す（pairwise summation）ので、原本のように先頭から順に足すのとは
結果が違う。0.1 を千回足すだけで差が出る。

```
素朴   99.9999999999986
np.sum 100.00000000000001
```

縮約はスカラーのまま原本の順序で回す。`検証/移植/test_rdfl_fast.py` が
この2点（要素ごとは一致する／縮約は一致しない）を試験で押さえている。

**縮約でも、呼び出しの間接費は削れる。** `T[i] = add(T[i], X)` は1回
ごとに view 3回・`np.empty`・`np.add`・構造体の書き戻しをやるが、
`str_op.flat_view` で `T` の view をループの外に出せば、ループの中は
`np.add(dv, x, out=dv)` の1回で済む。**足す順は1ビットも変えない**
（同じスロットに同じ順で同じ加算をするだけ）。③の `stat`・`printout`・
`shke` の集計はこれで縮めた（下の「③の最適化」）。
`test_nat_strop.py` が「同じ順なら一致する／逆順なら違う値になる」を
押さえている。

**まとめてよいかの判定は1つ。** 出力のスロットごとに、当たる演算の列が
変わらないか。前年度を読んで当年度に書くなら年齢の軸をまとめられる
（読む先と書く先が別）。同じスロットへ何本も足し込む（年齢を潰して
集計するなど）なら、足す順が変わるのでまとめてはいけない。

#### `cal_sum_*` の 64 通りの周辺和を `np.add.accumulate` で作る

④で一番の山は `Atamawari.c` の `cal_sum_kyufu`。6つの軸それぞれに
「計（添字 0）にまとめるか、元の値のままか」の 2^6 = 64 通りを回して
元の値を足し込む三十六重ループで、素の Python では1年度あたり40万回、
全体で2.6億回の加算になり手に負えない。

```c
for( seido[0] = KOKUNEN ; … ) for( nenrei[0] = UNDER_63 ; … ) …   /* 元の値 */
  for( seido[1] = 0 ; seido[1] <= 1 ; seido[1]++ ) …               /* 64 通り */
      array[seido[2]][…][shikyu_keitai[2]] += array[seido[0]][…][shikyu_keitai[0]] ;
```

ここは**「62 通りの周辺和」に読み替えられる**（飛ばす2通りは
`検証/原本の不具合.md` I1）。足し込み先と元の値は添字 0 を含むかで
必ず分かれるので重なりが無く、1つの足し込み先に入る元の値は
「元の値の添字を C の行優先で回る順」に並ぶ。

そこで**まとめる軸を昇順に前へ出してから1本に畳み、
`np.add.accumulate` の最後の要素を取る**。

```python
def _marginal(src, axes):
    ax = tuple(sorted(axes))
    rest = tuple(a for a in range(src.ndim) if a not in axes)
    x = np.ascontiguousarray(np.transpose(src, ax + rest))
    x = x.reshape((-1,) + tuple(src.shape[a] for a in rest))
    return np.add.accumulate(x, axis=0)[-1]
```

`np.sum` は対和（pairwise）で順番が違うので**使えない**
（この README の「ベクトル化はビット一致を壊さない（縮約以外は）」）。

`test_kiso_num.py` の `test_周辺和が原本のループと1ビットも違わない` が、
**原本の三十六重ループをそのまま素の Python で回した結果**と突き合わせて
いる（軸を小さくして 720 × 64 = 4.6万回）。

#### `.AT()` と `VEC()` は NumPy にそのまま対応する

事前調査では「`.AT()` が 5,221 か所ある」のが②の壁だったが、
中身は `ext/_vecarray.h` の

```c
#define AT3(axis1, axis2, axis3) at(axis1).at(axis2).at(axis3)
#define VEC_CONS3(type, a1, a2, a3, def) VEC_TYPE3(type)(1+a1, VEC_CONS2(type, a2, a3, def))
```

だけ。`.AT(i, j, k)` は素の多次元添字で、`VEC(double, a1, a2, …)` は
各次元を **`1 + a`** 個で作る `std::vector` の入れ子。つまり

    VEC(double, ENDY, 115, 6, 13, 58)  →  NumPy shape (126, 116, 7, 14, 59)

と1対1に移せる。**壁ではなかった。**

#### 寸法は `zero.cpp` にしか書いていない

    d3x / d3xs   (126, 116, 7, 14, 59)   各 676MB
    kfprx        (126, 116, 7, 14,  9)       103MB
    gee 系 18本  (126,   4, 116, 101)    各  47MB（計 851MB）

#### ②で見つけた「出力が壊れる」不具合（H3）

`pstat.cpp:11-35` の3つの小関数が

```cpp
return csvio::join("%16.8lf", vals).c_str();
```

と書いている。`csvio::join` は `std::string` を**値で返す**ので、
`.c_str()` が指すのは `return` 文の終わりで壊される一時オブジェクトの
中。**解放済みの領域**を `fprintf` に渡している（use-after-free）。

**無害ではなかった。** 原本と移植版の出力を突き合わせると、
`pstat()` が書く3本だけが食い違う。

```
総給付費,     26.40777389,     24.36361335,兆円   ← 移植版
総給付費,<cd ed d9 63 a1 55>,兆円                 ← 原本（ある1回）
総給付費,<e1 63 18 5e 33 56>,兆円                 ← 同じバイナリの別の回
```

**同じバイナリ・同じ入力でも実行のたびに変わる。** 化ける位置は
いつも同じ130行で、バイト列だけが変わる。末尾が `0x55` `0x56` に
なるのは PIE のヒープの番地の上位バイトで、**解放済みの区画に
残ったポインタを文字として読んでいる**ことの裏付け。
`setarch -R` で ASLR を切ると2回とも同じ出力になる。

| ファイル | 行数 | 化けた行 |
|---|---:|---:|
| `hikaku.*` | 216 | 130 |
| `ashimotosum.*` | 581 | 360 |
| `ashimotossum.*` | 581 | 360 |

見出し・単位・行数は合っていて、**数値の欄だけ**が数バイトのごみに
化ける。`hikaku` と `*sum` は、同じプログラム・同じ入力でも
**実行のたびに違うファイルになる**。

この3本は確認用のファイルで、②のほかのプログラムも③〜⑥も読まない。
**財政検証の結果そのものは影響されない。** 同じ `pstat()` が書く
`ashimoto` `ashimotos` は `hikaku_ns` を通らないので**バイト一致する**。

移植版は正しい文字列を渡す。したがってこの3本は原本と一致しないので、
`test_pstatの3本だけがB9で化けている` が「行数は同じ・化けるのは

#### ③の特徴 — `struct` を値で受け渡す

②が巨大な多次元配列（`.AT()` が 5,221 か所）で押すのに対し、
③は **8つの `struct` を値で受け渡す**。

```c
struct hihokensha { double ninzu; double kikan; double noufu;
                    double menjo[MENJO_DANKAI][KOKKO_HIKIAGE];
                    double gakusei; double wakamono; double fuka; };
```

これに対して `scalar` `scalar_2` `add` `multiply` `nendokan`
`nendokan_64` `adjustbenefit` `average_by_ninzu` が**型ごとに
多重定義**されている（C++ の関数多重定義）。

移植版は NumPy の**構造化 dtype** に写し、`dtype` で振り分ける。

```python
HIHOKENSHA = np.dtype([
    ("ninzu", "f8"), ("kikan", "f8"), ("noufu", "f8"),
    ("menjo", "f8", (MENJO_DANKAI, KOKKO_HIKIAGE)),
    ("gakusei", "f8"), ("wakamono", "f8"), ("fuka", "f8")])
```

`sizeof(struct)` が「欄数 × 8」であること（**詰め物が無いこと**）を
ハーネスで確かめてあるので、C の構造体のバイト列と NumPy の
dtype の並びが一致し、CRC32 で突き合わせられる。8つとも一致した。

    hihokensha 168 = 21 × 8      rorei      152 = 19 × 8
    rorei_kyu   56 =  7 × 8      gonen       16 =  2 × 8
    shogai      40 =  5 × 8      izoku       24 =  3 × 8
    kafu       136 = 17 × 8      ichijikin   24 =  3 × 8

年度の添字は**西暦から引く**（`nendo - SHONENDO`。`SHONENDO` = 2020）。
②の `k` = 西暦 − 2000（負にもなる）とは別の流儀。

移植直後の③は原本の89倍かかっていた。**ビット一致を1つも崩さずに**
2.8倍速くした。段階ごとの実測（105年度 × 4種別、出力11本・20MB を

| ＋障害・遺族・寡婦の年度末を軸まとめ（`ec0095b`） | **70.0s** | **36×** | バイト一致 |

（`efd946a` と `c1076d5` は合わせて測った。`efd946a` 単独のフル実測は
無い。障害・遺族・寡婦の3ブロックは合わせて 3.4秒＝4.6%で、行単位の
計測で「1つ1つは小さい」と見えていたとおり。）

**最初の見立ては外れた。** `siml` の五重ループを疑ったが、プロファイルは
`str_op`（構造体を値で受け渡す演算）を指した。`add` が1,168万回、
`numpy.zeros` が2,928万回、`add` 1回に 5.25us で、ほぼ全部が NumPy の
欄アクセスの間接費。**関数単位のプロファイルでは「`siml` のどのループか」
が分からない**ので、`sys._getframe(1)` で呼び出し元の行番号を数えたら、
`siml.py` の14行に約1,500万回（**61%**）が集中していた。

やったことは3種類。どれも `test_nat_strop.py`（38件）と段階テストで
原本との一致を押さえてから、フルのバイト比較で確かめた。

1. **構造体演算を平べったい float64 として扱う**（`str_op`）。構造体は
   「欄数 × 8バイト、詰め物なし」なので、float64 が n 個の subarray として
   view すれば1回のベクトル演算で済む。各欄の出力は double 1〜2個の1回の
   演算（縮約ではない）なのでビット一致は自動的に保たれる。ただし
   **5スロット未満の型は欄ごとに回すほうが速い**（view と ufunc の呼び出しに
   2.1us の床がある）ので、両方の実装を残して型ごとに選ぶ
2. **軸をまとめる**（`scalar_arr` などの `*_arr`）。「前年度を読んで
   当年度に書く」ループは読む先と書く先が別なので、年齢×期間や
   年齢×受給年齢の両軸をまとめられる。各スロットに当たる演算の列が
   変わらないのでビット一致する。老齢基礎の年度末（3,025回/年）と、
   加重平均のブロック（2,601マス × 14回/年）に当てた
3. **縮約の間接費を削る**（`flat_view`）。`stat`・`printout`・`shke` の
   集計は1つのスロットへ年齢×受給年齢を全部足し込む縮約で、足す順が
   結果を決めるのでまとめられない。けれど view をループの外に出せば
   ループの中は `np.add(dv, x, out=dv)` の1回で済む。**足す順は1ビットも
   変えない**

**残りの 36倍**は、まとめられない縮約（`printout` の年度間の直しは
`_c_at` の配列外読みを含み、`stat`・`printout`・`shke` の全体計は
1スロットへの逐次の足し込み）、`str_op` の1個ずつの呼び出しに残る
view と `np.empty` の間接費、それに `siml` 本体のループの間接費。
「前年度を読んで当年度に書く」形のループはこれで全部まとめた。

## システムごとの事前調査

### ② 厚生年金 給付費推計 — `.AT()` マクロ

`.AT()`（`std::vector::at()` の連鎖、最大6次元）を使っているのは
**②だけ**で、全体 5,221 箇所がここに集まっている。移植では NumPy の添字が
同じ範囲検査をしてくれるが、**負の添字は Python では末尾からの参照になって
黙って通る**。添字が負になりうる箇所は明示的に確かめる。

（当初 ⑥ が `.AT()` を使うと書いていたが、実際に走査すると ⑥ には1箇所も
無かった。訂正済み。）

### ⑥ 分布推計 — 乱数と匿名化

⑥は他の5システムと性質が違う。

**1. 乱数を使う。** `分布推計/main.cpp:90,153`

```cpp
std::mt19937 gen_rand(0);
std::shuffle(vector023.begin(), vector023.end(), gen_rand);
```

シャッフルした並びを `objects02[i].set_var002(vector023[i])` で個人の属性に
割り当てるので、**1つでも順序が違えば出力が変わる**。種は 0 固定なので
再現性はあるが、`std::shuffle` と `std::uniform_int_distribution` は
**規格が実装を決めていない**。NumPy や Python の `random.shuffle` とも違う。

`検証/移植/clib/cppstd.py` で libstdc++ の実装をそのまま写し、
**その場の libstdc++ をコンパイルして問い合わせる**テストで一致を確認した
（`検証/移植/test_cppstd.py`、要素数36通り＋連続10回、不一致0）。

ここで1つ落とし穴を踏んだ。最初は `uniform_int_distribution` を
「scaling して棄却」の古い実装で書いたが、`n <= 101` では全部一致するのに
`n = 275` と `n = 1000` で外れた。最近の libstdc++ は生成器がちょうど 32bit の
とき **Lemire の nearly divisionless 法**を使っていた（`_S_nd`、
`/usr/include/c++/13/bits/uniform_int_dist.h:255`）。小さい範囲では昔の方法と
偶然一致するので、大きい要素数を試すまで気付けない。

> **これは原本の性質でもある。** 公表プログラムを別の標準ライブラリ
> （libc++、MSVC、古い/新しい libstdc++）でビルドすると、⑥の出力は変わる。
> 移植版が一致するのは「同じ libstdc++ でビルドした原本」に対してである。
> 確認したのは gcc 13.3.0 / libstdc++ 20240904。

**2. 識別子が匿名化されている。** `func03a`〜`func13c`、`class01`/`class02`、
`main_var001`、`vector023`、`loop_var001`、`set_var002`/`get_var041` …
意味のある名前が1つも無い。⑤（`Escutrrh`、`shus_ave` など）とは違って、
コメントに「何をしているか」を書くには読み解きが必要になる。だから移植の
コメントは「原本の何行目か」と「観測できるふるまい」を書く方針にした。

**3. 個人単位のマイクロシミュレーションで、規模が大きい。** 実測した。

| コホート（性別・基準年齢） | 人数 | 追う年数 |
|---|---:|---:|
| 1・17歳 | 480 | 48 |
| 1・27歳 | 139,398 | 38 |
| 1・37歳 | 159,882 | 28 |
| 1・47歳 | 205,136 | 18 |
| 1・57歳 | 169,402 | 8 |
| 1・62歳 | 146,581 | 3 |
| 2・各歳 | 801,077 | 同じ |
| **合計** | **1,621,956 人** | 延べ約3,000万人年 |

**C 版は 100 秒**（`main.cpp:232` が自分で測って出す `time:100`）。

ここが⑤と決定的に違う。⑤は配列に対する演算だったので NumPy で受けられたが、
⑥は**個人ごとに違う分岐をたどる**ので素直なベクトル化ができない。
移植前は忠実移植（スカラー）だと Python で**数時間**かかると見ていた。

そこで次の順で進めた。

1. まず忠実に移植する（スカラー、読みやすさ優先）
2. **一番小さいコホート**（基準年齢17歳。性別1で473人、性別2で112人）で
   C と突き合わせてビット一致を確かめる。コホートは完全に独立
   （`objects02` も `mt19937(0)` も `loop_var002` のループの中で作り直す）
   なので、移植版を17歳だけに絞って走らせても照合として有効
3. そのうえで全量を1回流して実測する

**結果は 866 秒（14分）**で、見込みよりずっと速かった（上の「速度 — 実測」）。
36ファイル全部が `-O2` で建てた原本とバイト一致したので、
個人を軸にしたベクトル化には**手を付けていない**。

なお、もしベクトル化するなら `std::shuffle` と3回のソート、
累積人数による状態割り当て（`func09b`）は個人をまたぐので、
そこだけは順序を保つ必要がある。

#### ⑥ の未定義動作は観測できないことを確かめた

`prog02.cpp` のコピーコンストラクタは `set_var001`〜`set_var032` のあと
**`set_var035`** に飛んでいて、`var033` と `var034` を写さない。メンバ
初期化子も無いので、C++ ではコピー後にそこが**不定値**になる。
しかも `class02` はコピーコンストラクタを宣言しているため**ムーブが暗黙に
作られない**ので、`std::stable_sort` の要素の入れ替えも `std::vector` の
再確保もコピーを通る。つまりソートするたびに壊れる。

**それでも出力には出ない。** `main.cpp` の年次ループは

```
198行  stable_sort(… compare_var037())   ← ここで壊れる
200行  func09c(…)                        ← 全員に set_var033/034（if の外）
218行  func10d(…)                        ← ここで初めて読む
```

の順で、読むのは `func10d`（`prog10.cpp:547-553`）だけ。`func09c`
（`prog09.cpp:181-182`）は if/else の外で全員に無条件に代入する。
だから「壊れる → 必ず書く → 読む」になっていて、壊れた値は出力に届かない。

Python ではソートが参照を並べ替えるだけでコピーが起きないので、この未定義
動作に対応する挙動がそもそも無い。移植版は値を保持する。上の順序のおかげで
出力は一致する。

#### `func03a` は区切りの無い行でフィールドを2回返す

`prog03.cpp:8` が `find_first_of`（`size_t` の `npos`）の戻り値を
**`int` に入れている**ので -1 になり、添字の計算が1周ずれる。

```
"abc"   → ["abc", "abc"]      ← 2回返る
"1.5"   → ["1.5", "1.5"]
"a,b"   → ["a", "b"]          ← カンマが1つでもあれば普通
"a,"    → ["a"]
","     → [""]
```

原本をそのままリンクして25通り＋実データ3ファイル3,423行で確かめた
（`検証/移植/test_bunpu_io.py`）。
