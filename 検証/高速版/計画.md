# 高速版（数式モデル実装）の計画

## Context

厚生労働省の2024年財政検証プログラム（C/C++、6系統）は `検証/移植/` に
**ビット一致**で Python 移植済み（213件のテストで原本とバイト一致）。ただし
ビット一致を守る代償で遅い（原本比 ①8× ④4〜6× ⑤15× ③36× ②27×。原本自体は
1ケース93秒、うち②が83秒）。利用者の要望は、次の3つを同時に満たす**別実装**:

- **速い** — 原本Cと同等以下（感度分析で何十ケースも回す用途。2026-09-29 に目標を改めた。下の「速度目標と測り方」）
- **ロジック忠実** — 数理モデルどおり。ビット一致・丸め順序は捨てる
- **制度変更に柔軟** — パラメータ差し替えだけでなく、新しい給付種別や
  被保険者区分を足せる構造

### 利用者の決定（AskUserQuestion）

| 論点 | 決定 |
|---|---|
| 対象 | **①〜⑤**（⑥分布推計は乱数の個人シミュレーションで別物。忠実移植のまま） |
| 許容誤差 | **傾向が合えばよい**（所得代替率 ±0.5%pt 程度） |
| 依存 | **numba を許す** |
| 柔軟性 | **構造の変更まで**（給付を共通の型で扱う） |
| 原本の癖 J1〜J4・B10・B11・D6（意図と違う答え） | ~~**意図どおりだけ**実装。癖の再現スイッチは作らない~~ → **2026-09-29 に改めた: 既定は原本どおり**（公表値の再現）。意図どおりの値は overlay `fix_bugs` で重ねる。切り替えるのは出力に効く J1・J2・J3・B11（B10・D6 は効かない、J4 は高速版が書かない出力） |

### 大前提（利用者の指摘）: 高速版は「完全に再構築のサブセット」

`年金財政検証_数式モデル.md` は原本Cから**復元した派生物**で、原本そのものではない。
仕様書が読み違えている・取りこぼしている・「推定」で止まっている箇所は、
仕様書から作った高速版にそのまま穴として残る。だから:

1. **正解は常に原本（＝ビット一致の移植版）。仕様書は入口。** 高速版の公開関数は
   docstring に `港: <dir>/<file>.py:<func>` と `仕様: §x.y` の**両方**を持つ
   （テストが検査する）。仕様書と移植版が食い違えば移植版が正で、仕様書の修正は
   別コミット。食い違いは `対応表.md` 付録「仕様書との食い違い」に file:line で残す
2. **対応表は仕様書の節ではなく移植版の関数一覧から作る。** 仕様書の「推定」の印は
   仕様書が書いた箇所にしか付かず、書いていない分岐は印すら無いから。公開関数
   319（① 55・② 79・③ 76・④ 33・⑤ 76）を1つずつ 実装／意図して省略／該当なし
3. **検証は看板の数字だけで済ませない。** 中間の系列（被保険者数・新規裁定・
   年度末受給者数・給付費）を移植版の出力CSVと突き合わせる段階を各フェーズに入れる

仕様書の自己申告の穴（実測）: 付録Bの未解決は1件で⑥のみ。①〜⑤で「推定」は
2箇所（③の再加入が起きない理由 L408、遺族厚生の65歳以上係数の出所 L995）で、
どちらも式ではなく「なぜ」の推定。§15.7 で全節をレポート第7章と照合済み。

## 受け入れ基準

「傾向が合えばよい」でも**離散の出力は別扱い**。法定の丸めは「精度」ではなく
「ロジック」なので高速版でも規則を実装する（丸めの**順序**は捨てる）。

| 出力 | 比較先 | 判定 |
|---|---|---|
| 最終所得代替率 計/比例/基礎（8ケース） | 移植版⑤（`emp_shushi/shus_calc.py:369-389`） | \|差\| ≤ 0.5%pt |
| 所得代替率の時系列（`03summary`） | 同 | \|差\| ≤ 0.5%pt |
| 給付水準調整の終了年度（厚年・国年） | 同 | **±1年**（128回の二分法の整数出力は演算順で隣年に飛びうる）。連続量の余裕 `積立金[2119] − 支出[2120]×D` も系列で比べる |
| 財政見通し（`01shushi` 30列×5制度） | 同 | 相対 1e-3（終了年度±1の帯は 1e-2） |
| 老齢基礎満額・改定率（2024年度まで）・保険料月額 | 移植版③④⑤・実績 | **完全一致**（100円・0.001・10円の法定丸め） |
| 収入計/支出計/国庫/福祉 = 部分和、③計 = Σ種別、④周辺和 = Σマス | 内部恒等式（`検証/数式編/verify_cc.py` と同じ） | 相対 1e-9 |
| 中間系列（各フェーズの表を参照） | 移植版の出力CSV | フェーズごと |

癖の修正（J1〜J4・B10・B11・D6）で移植版との差は必ず出る。台帳の実測
（J3: 受給者数 +0.3〜1.4%、B11: 遺族基礎(妻) 0.4〜2.0%）は ±0.5%pt に収まる
大きさだが、**各修正の効果を単独で測っておく**（移植版の使い捨てブランチで
トグルして測る。高速版側では測らない）。

### 軸の統一（`axis.py`）— 再実装で最初にやる

配列オフセット／④人数と経済で2原点・年齢も2原点／⑤西暦−2000）。

- `test_no_raw_origin.py` がパッケージ内の `- 2000`, `- 2020`, `- SHONENDO`,
  `- UNDER_67`, `C19(` 等を grep して落とす

- ⑤の `x<67 → dx=66` の潰しは `Ages.collapse_below(67)` として明示

### 給付の共通の型（`benefit.py` / `algebra.py`）

```python
@dataclass(frozen=True)
class BenefitSpec:
    name: str; system: Literal["kokunen","kounen"]
    amount_fields: tuple[str,...]      # ③: noufu/menjo/rofuku_shitasasae/fuka ／ ②: j=1..23 の名前つき部分集合
    slide_fields: tuple[str,...]       # 改定率・マクロが掛かる欄
    kakyu_fields: tuple[str,...] = ()  # 加給（改定率2）
    fixed_fields: tuple[str,...] = ()  # 付加（改定もカットも掛けない）
    age: AgeRule
    extra_axes: tuple[tuple[str,int],...]   # (("jukyu_nenrei",11),) (("tokyu",2),) (("kuriage",16),)
    classes: tuple[str,...]            # 適用する InsuredClass
    kiso_tag: KisoTag | None           # ④の直積のマス (制度, 新旧, 区分, 対象, 形態)
    shushi_col: str | None             # ⑤の Cc 列名（etoc の置き換え）
    rounding: dict[str, RoundingRule]
    spec_ref: str; port_ref: str

class BenefitModel(Protocol):          # ライフサイクル
    def shinki(self, y, cls, ctx)                       # 新規発生 — 各給付が必ず書く唯一のフック
    def yearend(self, y, prev, shinki, rates)           # 既定: 前年度×(1−失権率)×改定率 + 新規
    def nendokan(self, prev_end, cur_end, kt, kt2)      # 既定: 2か月遅れの重み、付加は改定しない
    def cut(self, arr, cut_ruiseki)                     # 既定: adjustbenefit（人数・付加は素通し）
    def aggregate(self, state)                          # 既定: extra_axes と classes を潰して (年度, 年齢)
    def emit(self, totals)                              # 既定: (kiso_tag, shushi_col)
```

`algebra.py` は `nat/str_op.py` の8演算を欄リスト駆動にしたもの。`test_algebra.py` が
`nat/str_op.py` と乱数入力で rtol 1e-12 の一致を確かめる（`test_nat_strop.py` の
入力を流用）。

**4系統の当てはめ**
- ③: 9つの struct 型 × 給付 → 約20本の `BenefitSpec`（老齢基礎 全部/一部、旧法老齢、
  通算老齢、5年、障害 一般/20歳前/旧法 ×等級、遺族 妻/夫/子、寡婦 新/旧、
  死亡一時金 7区分、付加は老齢の欄）。`nat/glva.py:314-360` の機械的に並ぶ配列群が
  `BenefitState` に、`nat/siml.py:743-972` の反復が `for spec in registry` に畳まれる
- ②: `i=1..13` → 13本の `BenefitSpec`（`extra_axes=(("kuriage",16),)`）。
  `shke*` の三重ループは (年度, 制度, i) ごとに (x, xx) をベクトル化
- ④: `KisoTag` に scatter-add したあと `add_marginals()` **1回**で62本の周辺和を置き換え
- ⑤: `CcCol` 列挙（`verify_cc.py` の検証Aから命名）、`shushi_col` でグループ和

## numba と numpy の線引き（README に書く規則）

`kernels/` に `@njit(cache=True)` で置くのは、
(a) 添字 `y` が `y−1` を、または `x` が `x−1` を読む**本物の漸化式**で、1段ごとの numpy
間接費が支配的になる長さのもの、または (b) 解法の反復の内側で回る本体、**だけ**。
それ以外は要素ごとの軸で素の numpy（③ 年齢51×期間51・年齢×受給年齢11、② 年齢×期間
75×75 と (x, xx)、① 年齢121、⑤ `shus_ave` の k）。カーネルは float64 の素の配列だけを
受け取り（構造体 dtype は njit に入れない）、各カーネルに `_ref.py` の純 numpy 双子を置いて
`test_kernels_ref.py` が rtol 1e-12 で一致を見る（`KOSOKU_NOJIT` の両方で）。

| カーネル | 移植版の参照 | 理由 |
|---|---|---|
| `k_fund_recur` 積立金 `Cc[20,k]=Cc[20,k-1]+Cc[19,k]` | `emp_shushi/shus_calc.py:shus_shushi`、`kiso_nenkin/tyousei.py:96-110` | (a)(b) |
| `k_macro_carry` `T[n]=T[n-1]/max_cut[n]·pre_cut[n]` | `kiso_nenkin/econ.py:116-180` | (a) |
| `k_atamawari_cut` | `kiso_nenkin/atamawari_cut.py` | (b) 二分法で128回以上 |
| `k_shus_ave` | `shus_calc.py:shus_ave` | (b) 割線法＋二分法で62回 |
| `k_rh_tokutyo` | `shus_calc.py:shus_calc8` 205-260 | (a) |
| `k_age_recur_year` `f[x]=f[x-1]·残存·改定+fn[x]` | `emp_kyufu/simlg.py`、`simlrhnf.py` | (a) 年度ごと 115×16×13 |

解法の外側（④ `tyousei` の年度走査＋二分法、⑤ `shus_calc8` の割線法14回＋二分法）は
Python のままカーネルを呼ぶ。③の年度末ループ（105回 × numpy 演算）は numpy のまま。

**numba が無い環境**（いまの作業環境も無い）: `kernels/jit.py` が恒等デコレータに落ちる。
正しいが遅い（④ 30〜60秒、⑤ 10秒の見込み）。正しさのテストは両モードで回し、
速度のテストは numba 必須。`numba` は extras。

## 財政構造の可変化（第2ラウンドの決定・フェーズ H〜K）

高速版は「新しい年金制度を考えるための土台」。制度パラメータと給付種別だけでなく、
**財政構造**（誰が誰に何を払うか、何を動かして均衡させるか）も変えられるようにする。

### 利用者の決定（AskUserQuestion、第2ラウンド）

| 論点 | 決定 |
|---|---|
| 変える系統 | **4つ全部**: 財源と均衡の方式／給付設計／勘定の組み替え／制度の外側（被保険者区分） |
| 実装順 | 希望なし → 推奨どおり **均衡 → 勘定 → 給付 → 外側**（フェーズ G の後） |
| 変更後の検証 | **恒等式と回帰のみ**。既定（現行制度）なら移植版と一致。変更後は式の目視と玩具ケース |
| 勘定の粒度 | **現行5制度＋基礎年金勘定を既定に**。統合・分割・新設は登録簿の操作 |
| 拠出履歴 | **コホート×経過年で持つ**（②の配列と同じ形）。NDC・最低保障・世代別倍率の土台 |
| 均衡の解法 | 4組: 現行（料率固定・給付水準調整）／給付固定・料率均衡／賦課方式（毎年均衡）／永久均衡 |
| 時間軸 | **2125年度で固定**。永久均衡は「終期以降は定常」で近似 |
| 看板の指標 | 所得代替率・終了年度／給付総額÷GDP・保険料÷総報酬／世代別の給付負担倍率／積立度合・積立金実質額 |

### 大前提（変わらない）

- **既定＝現行制度。** 構造の切り替えは全部データ（yaml）で、既定のままなら
  移植版との一致テスト（フェーズ A〜G の許容）が通り続ける。構造を変えた瞬間に
  正解（移植版）は無くなるので、変更後に言えるのは (1) 恒等式が成り立つ
  (2) 既定に戻せば移植版に戻る (3) 玩具ケースが手計算と合う、の3つだけ
- 厚労省のオプション試算は「構造の中の変更」。財政方式や勘定の変更は公表値が
  無いので「傾向が合えばよい」の基準すら置けない。README にそう書く

### H. 均衡の解法 `BalanceRule`（⑤ `shus_calc8`・④ `tyousei` の一般化）

現行の解法は「料率を固定し、給付水準（マクロ経済スライドの終了年度）を動かして、
2125年度の積立度合が 1 になる点を探す」。これを **(動かすもの, 合わせる条件)** の組に分ける。

```python
class BalanceRule(Protocol):
    lever: Literal["benefit_level", "premium_rate", "kokko_share", "start_age"]
    target: Literal["fund_ratio_at_end", "annual_balance", "perpetual"]
    def solve(self, state, policy, kernels) -> Solution    # 二分法／割線法／逐次
```

| 組 | 動かす | 合わせる | 解法 | 備考 |
|---|---|---|---|---|
| 現行（既定） | 給付水準（終了年度） | 2125年度 積立度合 = 1 | ④二分法 + ⑤割線法（`k_atamawari_cut`, `k_shus_ave`） | 移植版との回帰の基準 |
| 給付固定・料率均衡 | 料率（一定値、または引上げ停止年度） | 同上 | 割線法 1本 | **天井なし**。均衡する料率をそのまま出す（天井の判断は利用者） |
| 賦課方式 | 毎年の料率 | 各年度 収入 = 支出 | 逐次（解法なし） | **積立金は実質額（物価）を一定に保ち、運用収入は収入に入れる**。料率 = (支出 − 運用収入 − 国庫 − 積立金の名目維持分) ÷ 総報酬 |
| 永久均衡 | 給付水準 or 料率 | 定常状態で 積立金 × (r − g) = 収支差 | 2125年度以降を定常と仮定して閉じる | 人口・経済前提は最終年度で据え置き |

`Options` の7本のレバー（§11.1）は BalanceRule と直交する（どの組でも掛かる）。

### I. 勘定と流れ `Account` / `Transfer`（⑤の30列の生成）

`verify_cc.py` の恒等式がそのまま定義になる:
収入計 = 保険料 + 運用収入 + 国庫負担 + 支援入 + 納付金 + 妻積み、
支出計 = 独自給付 + 基礎年金拠出金 + 福祉 + 支援出。

```yaml
accounts:
  kounen:   {kind: employee, classes: [...], premium: {rate_schedule: ...}}
  kokkyo:   {kind: employee, ...}
  chikyo:   {...}
  shigaku:  {...}
  kokunen:  {kind: national, classes: [...], premium: {monthly: ...}}
  kiso:     {kind: pool}                      # 基礎年金勘定
transfers:
  kiso_kyoshutsu: {from: [kounen, kokkyo, chikyo, shigaku, kokunen], to: kiso,
                   rule: atamawari, base: kyoshutu_taisho}     # ④の按分
  kokko_kiso:     {from: treasury, to: kiso, rule: share_of_benefit, share: 0.5}
  shien:          {from: [kounen], to: [kokkyo, chikyo, shigaku], rule: ...}  # 一元化の支援金
```

- ⑤の30列は勘定と流れから**生成**する（`etoc` の多対一は `BenefitSpec.shushi_col`
  → `Account.flows` に置き換わる）
- 「統合」は `accounts` から1件消して `classes` を移す操作、「税方式化」は
  `kiso_kyoshutsu` を消して `kokko_kiso.share: 1.0` にする操作。コードは変えない
- 恒等式テスト: 各 Transfer の from 側の和 = to 側の和（相対 1e-9）、各勘定の
  収入計・支出計 = 部分和、積立金漸化式
- 既定の yaml で⑤の `01shushi` が移植版と一致すること（フェーズ C の許容）が回帰

### J. 給付設計 `BenefitFormula`＋拠出履歴

- ②の (制度, 年度, 年齢, 経過年) の配列に **拠出額の累積**（名目、および
  賃金上昇率で評価したもの）を1本足す。標準報酬は②が既に持つ
- `BenefitFormula`: `earnings_related`（現行の報酬比例）／`flat`（定額）／
  `ndc`（仮想口座残高 ÷ 年金現価率）／
  `minimum_guarantee`（基礎＋比例が閾値未満なら補填。**財源は国庫（税）を既定**にし、
  `transfers` の from を `treasury` か `kiso` かで選べる）
- **NDC の決定**（利用者）: 指標化率は**賃金上昇率**（経済前提の名目賃金上昇率。
  記帳後の残高の増加率と、裁定後の年金額の改定率の両方に使う）。年金現価率の
  生命表は**コホート別**（同梱の年度×年齢の死亡率 `QX-*` を生年で斜めに読んで
  作る。2125年度より先の死亡率は最終年度で据え置き。時間軸固定の帰結として明記）。
  見込み利回り（現価率の割引）は指標化率と同じ賃金上昇率にして、裁定後の改定と
  相殺させる。**前取りなし**（利用者の決定。スウェーデン方式の 1.6% は置かず、
  yaml の `ndc.frontload: 0.0` を既定に。変えればケース比較に前取りの効きが混ざる
  ことを README に書く）。**移行は既定どおり**（利用者の決定）: 導入時点で既加入者の
  「旧制度なら受け取れたはずの年金額」（②の年度×年齢×経過年の年金額）に
  コホート別の年金現価率を掛けて初期残高に換算する。旧制度の並走はしない。
  換算が旧制度の約束と同じ価値かは制度設計の主張なので README に「設計例」と書く
- 世代別の給付負担倍率はこの拠出履歴から出す（定義は下の指標の表）

### K. 制度の外側（①の被保険者区分）

### 玩具ケース（検証の代わり）

BalanceRule と Transfer の各1件に、**手計算できる最小の例**（被保険者1万人・
給付1本・5年度）を `tests/toy/` に置き、式の目視と数値の一致を両方残す。
構造を変えた設定で言える正しさはこれだけなので、省略しない。

### やらないこと（この節の範囲）

- 2125年度より先の人口・経済前提の持ち込み（時間軸は固定）
- 基礎率の導出（新しい被保険者区分の基礎率は入力）
- 変更後の設定に対する「公表値との照合」（存在しない）
- 高速版の分布出力を「⑥分布推計の代わり」と名乗ること（**利用者の決定**）。
  J の拠出履歴（コホート×経過年）から年金額の粗い分布は出せるが、⑥は初期母集団が
  同梱資料に無く公表値と比べられない（仕様書 §12.5）という制約と混ざるので、
  出力名・README ともに「コホート別の年金額（設計例）」とし、⑥の出力名は使わない

## 検証（実装を進めるときの手順）

各フェーズで: (1) 移植版のCSVを上流にして段階単体テスト → (2) 高速版の上流に切替 →
(3) `compare_fast.py --against port` → (4) C 以降は `--against published` も →
(5) 台帳の該当系統を埋めて `test_ledger.py` → (6) `bench.py`。
最後に既存の `pytest 検証/移植`（213件）が**変わっていない**ことを確認する
（高速版は移植版に触らない）。
