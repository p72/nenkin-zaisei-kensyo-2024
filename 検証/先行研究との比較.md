## 3. 報告書の説明を実測で検討する

報告書の説明のうち、原本とハーネスがあれば確かめられるものを3つ選んで
測った。いずれも**報告書の Python コードは見ていない**。確かめたのは
「原本 C はそう振る舞うか」だけである。

### 3.1 「nat の 2.36% は FMA の累積誤差」か

報告書は、国民年金（nat）で高齢・終期のセルに最大約 2.36% の相対誤差が
集中することを、「C 言語のコンパイラが FMA（積和融合）命令を使い、
Python は IEEE 754 の2段階丸めを厳格に行う。1演算あたり 1e-16 程度の差が
約100年分・116年齢階級の漸化式で蓄積した」と説明している（p.6・p.16）。
差の符号が年度をまたいで反転することを、論理誤りではなく浮動小数点の
ドリフトだと判定する根拠に挙げている（p.16）。

FMA で本当にその大きさになるかを、原本そのもので測った。
`検証/実行/nat_build_flags.py` が、同じ原本③を4通りのコンパイル指定で
建て、同じ入力（高成長実現ケース 3001）で 2021〜2125年度の105年度を
走らせ、出力10本（244万欄）を `-O2` の出力と欄ごとに比べる。
`objdump` で実行ファイル中の FMA 命令（`vfmadd*` / `vfmsub*` /
`vfnmadd*` / `vfnmsub*`）を数えて、本当に FMA が使われたことも確かめる。

| コンパイル指定 | FMA 命令の数 | 意味 |
|---|---:|---|
| `-O2` | 0 | 同梱 Makefile の release と同じ。x86-64 の既定では FMA は出ない |
| `-O2 -mfma` | 140 | FMA を使わせる |
| `-O2 -march=native` | 141 | この CPU の命令をすべて使わせる（AVX-512 含む） |
| `-Ofast` | 0 | FMA は出ないが演算順の書き換えを許す |

| `-O2` との比較 | 違う欄 / 全欄 | 最大相対差 | 最大絶対差 |
|---|---:|---:|---:|
| `-O2 -mfma` | 12,604 / 2,447,794 | **1.4e-12** | 1.6e-02 |
| `-O2 -march=native` | 12,604 / 2,447,794 | 1.4e-12 | 1.6e-02 |
| `-Ofast` | 180,593 / 2,447,794 | 2.4e-10 | 2.0 |

（ファイル別の内訳はスクリプトが出す。`ROREI_SHINKI` は 1,455,168 欄の
うち 11,201 欄が変わり最大相対差 8.9e-13。報告書の `ROREI_SHINKI` の
比較セル数 1,455,168 と一致するので、同じ形式の出力を見ている。）

**FMA の有無で変わるのは相対 1e-12 まで。** 2.36% とは10桁違う。
105年度の漸化式を丸ごと回してもこの大きさに収まるのは、③の漸化式
（前年度末 × 残存率 × 改定率 ＋ 新規）が差を増幅する形をしていないため
である。演算順の書き換えまで許す `-Ofast` でも 2.4e-10 に留まる。
②厚生年金給付費推計を `-O2` と `-Ofast` で建て比べたときも、105年度 ×
年齢 × 経過年の漸化式を通して相対 1e-11 以下だった
（[原本の不具合.md](原本の不具合.md) G2）。

もう1つの事実として、本プロジェクトの Python 版③は、演算順を原本どおりに
保つだけで出力11本が原本とバイト一致している。**Python 側の演算が
原本と本質的に違う、ということはない。**

以上から、**推定**: 報告書の nat の 2.36% は浮動小数点の累積ではなく、
実装の差（添字・初期化・分岐・読み込みのいずれか）である可能性が高い。
報告書自身も「セル比較で差が大きかった事例の多くは、浮動小数点ではなく
移植漏れ・参照ずれであった」（p.14 §4.4）と書いており、その延長で
読める。符号が反転することは、添字や分岐の違いでも起きる。

なお報告書の「FMA 使用はコンパイラ・最適化フラグ・CPU 世代によって
変わるため、同じ C ソースでも環境によって結果が異なりうる」（p.16）は
それ自体は正しい。ただし、その差の大きさは上の表のとおり相対 1e-12 の
桁で、公表値の桁（所得代替率は 0.1% 刻み、金額は億円・兆円単位）には
現れない。

### 3.2 調整終了年度のずれ

報告書は、基礎年金（bas）の `kekka` の 21.5% の不一致を、マクロ経済
スライドの調整終了年度（`S_C_NENDO`）が golden と Python 版でずれた
ことに帰している。ずれの大きさは本文内で揺れている。

| 箇所 | golden | Python 版 | 差 |
|---|---|---|---|
| p.14 §4.3 | 2039 | 2042 | 3年 |
| p.17 §5.2.1 | 2039 | 2040 | 1年 |
| p.20 §5.2.3 | 2039 | 2042 | 3年（「給付抑制の3年延長」） |

どれが最新かは本文からは決められない。原因については「終了判定の
ロジックは golden と Python 実装で完全に同一であり、境界条件（<）も
一致している」うえで、「上流モジュール（wakuc・bas）の100年超の長期
シミュレーションで浮動小数点演算の微小な累積差が積立金・支出の推移に
影響し、閾値到達年度がずれた」（p.20）、あるいは「R 側の長期計算における
収束のされ方に伴うもの」（p.18）と説明し、`kekka` を compare から除外して
pass としている（p.18）。p.14 では「Python 側は本来の C 言語の仕様に
忠実な終了条件を採用しているのに対し、参照側の R プログラムでは終了判定が
別年度まで延長されるケースがある」とも書かれている。

本プロジェクトでの実測。

- 報告書の代表例の試算番号は「1000-3001-1000」（試算番号・経済前提・
  外枠、p.10）。経済前提 3001 は本プロジェクトが「高成長実現ケース」として
  通している番号と同じである（`検証/実行/run_pipeline.sh 3001`）。
- 厚生労働省の公表値では、高成長実現ケースの基礎年金の調整終了年度は
  **2039年度**。本プロジェクトが `-O2` で建てた原本を通した結果も
  **2039年度**（`調整最終年度 国年： 39`）で、所得代替率 56.9% / 25.0% /
  31.9% を含め公表値と一致する（[README.md](../README.md)）。
- 報告書の golden（R ラッパーで回した公式 exe）の 2039 は、この公表値と
  一致する。

つまり golden の終了年度は「R 側が延長したもの」ではなく、公式 exe が
出す値であり、公表値でもある。R は計算ロジックを持たない（p.10）ので、
R が終了判定を変えることも考えにくい。**推定**: ずれは Python 版の側に
ある。3.1 のとおり浮動小数点の累積で積立金が動く大きさは相対 1e-12 の
桁で、終了判定（積立金が支出の所定倍率を回復したか）が1年動くのは、
その年度の余裕がたまたまその桁で 0 に近い場合に限られる。3年動くことは
それでは説明できない。試算番号と外枠番号が本プロジェクトの実行
（3001-3001-3001）と異なるので、条件が完全に同じとは断定できないが、
公表値とも一致している側が golden であることは動かない。

終了年度がずれると、以降の `cuta`・給付水準・支出・積立金が連鎖して
ずれる。報告書が §5.2.3 で「2040年を境にワニの口のように開く」と描く
乖離（p.20）と、`emp_shushi` の一致判定が `cuta` を除外した上のものである
こと（p.6）は、この1点に根を持つ。ここを直せばマクロ乖離の相当部分が
消えると**推定**する。

### 3.3 `kok` の読み

報告書は「接尾辞 kok を『国民健康保険（国保）』と読む表現が一部資料に
あるが、本プロジェクトでは正式な制度対応は確定していない」（p.8）と
書き、一方で p.27 表7 では「kok 国共 pseid 1 国家公務員共済」としている。
同梱資料の範囲では後者が正しい。②給付費推計の `pseid` は 0 厚生年金、
1 国家公務員共済、4 地方公務員共済、5 私学共済で、`kok` は国共済の
出力である（[年金財政検証_数式モデル.md](../年金財政検証_数式モデル.md) の
「厚年・国共済・地共済・私学。①②が扱う `kou`／`kok`／`ren`／`sig` に対応」、
[原本の不具合.md](原本の不具合.md) K1）。国民健康保険は年金財政検証の
計算に出てこない。

### 3.4 報告書に出てこない原本側の癖

報告書は「Python 版は C ソースの意図を正確に反映している」（p.6）と
書いている。忠実に写しているなら、原本の癖も一緒に写っているはずである。
本プロジェクトの台帳のうち**結果が変わる**4件は、報告書には出てこない。

| 台帳 | 内容 | 影響（実測） |
|---|---|---|
| J1 | ②定額部分の生年別読替率で 1.369 が 369 になっている | 該当生年の定額部分が正しい額の約27%で計上される（人数は老齢受給者の1%台） |
| J2 | ②`ab` に掛ける係数が地方公務員共済だけ3桁ずれている | 地共済の `kfprx` が約500倍で出る |
| J3 | ③繰下げ割引率が2032年度以降だけ添字を間違えている | 老齢基礎の受給者数が 2032〜2050年度で +0.3〜1.4% |
| J4 | ③`printout` が改定率と満額の年齢の添字を67ずらしている | 参考出力の年齢別の内訳が全列同じ値になる（④が読む `KISONENKIN` には出ない） |

これらは golden にも同じ癖が入っているので、golden と突き合わせる方法
では見つからない。原本の C を読んで台帳に積み、公表値と突き合わせて
「公表値は癖込みの値である」と確かめる必要がある
（[原本の不具合.md](原本の不具合.md) の「E. 直してはいけない」）。
報告書のチームが把握しているかどうかは本文からは分からない。

### 3.5 髙橋ほか（2023）の「最大 1/100 程度の差」

報告書は、髙橋ほか（2023）が2019年財政検証プログラムを Windows で再現
した際に公表結果と最大 1/100 程度の差が出たことを引き、それを「本
プロジェクトで取り組んでいる浮動小数点パリティ問題と本質的に同じ課題」
と位置づけている（p.9）。

2024年プログラムについては、本プロジェクトの `-O2` ビルドが公表値と
41,904項目で不一致0だった。2019年と2024年のプログラムは別物なので
直接の反証にはならないが、少なくとも2024年プログラムでは、同梱 Makefile
と同じ `-O2` で建てれば環境依存の差は公表値の有効数字に現れない。
3.1 の表のとおり、FMA を使っても `-Ofast` にしても 1e-10 の桁である。
**推定**: 1/100 の差が出るとすれば、それは丸めではなく入力データや
実行条件（ケース番号・オプション・パッチ）の違いである。

## 4. 互いに学べること

**本プロジェクトが報告書から学べること。**

- ミクロとマクロの2ルートで見る構え、とくにマクロ系列の乖離率を時系列で
  描いて構造（2040年で開く）を読む方法。本プロジェクトの照合は項目ごとの
  一致・不一致で、乖離の**形**は見ていない。
- 改善の経緯を数字で残す表（839% → 1.98%）。過程が追える。
- 残課題を1本の Runbook に集約する運用。本プロジェクトの残課題
  （②の公表値照合を `-O2` で取り直す、⑥は初期母集団が無く公表値と
  比べられない、など）は各 README に散っている。
- `emp_kyufu` が「数分」で回る実例。ビット一致を捨てれば②はそこまで
  縮む、という目安になる。

**報告書のチームに役立つと思われること。**

- `-O2` で建てた原本を直接の正解にすれば、ゴールデン経由の間接比較で
  見えない差（原本の癖、R 側の実行条件）が切り分けられる。本プロジェクトの
  ハーネス（`検証/移植/harness_*.c(pp)`）は原本を無修正でリンクして
  段階ごとの配列を取り出せる。
- nat の 2.36% と bas の終了年度のずれは、3.1・3.2 の実測から、浮動小数点
  ではなく実装差である可能性が高い。許容誤差と除外で運用するより、
  差の出る最初のセルを段階ごとの突き合わせで特定する方が早い。
- 原本側の癖の台帳（J1〜J4、B10・B11、D6）。golden と一致していても
  原本の意図と違う値を出している箇所がある。
